# 前端 UI 外壳迁移方案（分阶段，可执行）

> 文档类型：迁移方案（规划与执行依据，实施细节以矩阵与验证计划为准）
> 关联文档：`docs/frontend-ui-migration-matrix.md`（迁移矩阵，状态唯一权威）、`docs/frontend-ui-migration-verification.md`（验证计划，门槛定义）、`TODO.md`（批次计划，本方案仅引用其路径，不复制细节）、`docs/ui-design-p9.md`（视觉规范）
> 验证责任：主协调者（各阶段完成条件由主协调者签署；验证执行可委托对应 specialist，证据统一汇总至主协调者）
> 安全约定：本方案不包含任何密码、令牌、密钥等敏感参数；不涉及测试账号具体值

---

## 1. 迁移目标与总原则

### 1.1 目标

在保留 Next.js 运行时（`frontend/`，Next.js 15 + React 19 + TS 5）的前提下，将应用外壳（侧边栏、导航菜单、顶部用户区、底部管理条、浮动 Dock、用户头像、通知中心、个人设置等）按 you.com 基线（`/home/you.com/src/App.tsx`）重构升级，并保证全部旧业务零遗漏接入新导航。

### 1.2 三条总原则

| 原则 | 含义 | 落地要求 |
| --- | --- | --- |
| **新壳承载** | 新外壳（基于 you.com 基线的导航结构）只承担布局、导航、用户区、全局浮层等外壳职责 | 外壳组件与业务组件解耦；新壳不得内嵌任何业务逻辑 |
| **旧业务复用** | 既有业务组件原样复用，不因外壳迁移而重写、不顺手重构 | `page.tsx` 的 `renderMainContent` 各分支组件保持现状，仅调整挂载方式 |
| **单点切换** | 旧壳/新壳的切换收敛到唯一装配点（`page.tsx` 顶层），一次切换整体生效，保证可逆 | 不分散在多文件改开关；切换失败可整体回退（见第 9 节） |

## 2. 硬性视觉约束（不可违反）

**系统头部标题的字体大小与动效在迁移全程必须保持当前行为不变，任何阶段不得调整。**

- 所指对象：侧边栏头部系统标题「人事行政管理系统」（当前实现于 `frontend/components/layout/app-sidebar.tsx`，使用 `rolling-text text-base font-semibold`）。
- 保持内容：
  - 字体大小与字重：`text-base`（1rem / 16px）+ `font-semibold`，不得改动。
  - 滚动动效：`rolling-text` 类及其动画（`frontend/app/globals.css` 定义，`6s ease-in-out infinite` 循环、20px 滚动高度与关键帧行为）原样保留，不得调整时长、缓动或帧位。
- 若新壳需要复刻该标题，必须**原样复用**现有类名与动画定义，禁止另起一套样式或动效。
- 该约束适用于阶段 0–3 全部工作，纳入各阶段「明确不改范围」与验收核对。

## 3. 环境变量隔离原则（仅开发/预发布启用）

1. **迁移开关的启用范围**：新壳切换所需的功能开关（feature flag）类环境变量，只允许在**开发（development）与预发布（preview/staging）**环境启用；生产环境不配置该开关，固定使用最终形态（切换完成后的新壳）。
2. **变量名不预设**：具体变量名必须在实施阶段基于已验证的配置方案确定并登记，本方案不规定未经验证的具体变量名，避免文档与实现漂移。
3. **复用已验证机制**：环境隔离可复用仓库已有、已验证的机制（如 `NEXT_PUBLIC_API_BASE_URL` 指向不同后端、后端 `SIAPP_DATABASE_PATH` 指向独立库等）；本方案不展开其值。
4. **禁止事项**：本方案及后续实施脚本中禁止出现密码、令牌、密钥等敏感参数；涉及环境变量的示例一律使用占位描述而非具体值。

## 4. 统一视图映射与当前 page.tsx 兼容

### 4.1 兼容基线

- `frontend/app/page.tsx` 的 `currentView` 状态与 `renderMainContent` switch 分支是**唯一业务渲染入口**，迁移全程保留，不重构成路由或新状态模型。
- 新壳导航项点击后仍通过 `onViewChange(id)` 回调写入 `currentView`，`id` 必须落在现有视图值集合内：`landing / employee / insurance / dormitory / organization / audit / monitoring / daily-affairs / system / personal-settings / feedback / departments / knowledge`。
- 现有全局事件契约不得破坏：`dashboard:toggle-sidebar`、`dock:open-chat`、`dock:open-notification`、`dock:open-site-memo`、`dock:request-support`、`dock:go-home` 等。

### 4.2 视图映射表（新壳导航 → currentView）

## 5. 分阶段迁移计划

### 阶段 0：前置准备与基准固化

**交付物**
- 视图映射表定稿（第 4.2 节），逐项标注基线项 → 视图值 → 组件 → 三态状态。
- 回退基准：确认迁移前 commit 可构建运行，记录基准 commit（供第 9 节回退演练使用）。
- 环境变量隔离方案（第 3 节）在开发/预发布环境落地并验证。

**依赖**：无（需主协调者确认映射表与基准）。

**明确不改范围**：任何业务组件、后端代码、系统头部标题（第 2 节）。

**完成条件**：G0 前置门槛通过（后端 :8080 可启动、seed-e2e 幂等成功、`frontend/.next` 已清理）；回退基准 commit 已记录；映射表经主协调者确认。

### 阶段 1：新外壳实施（首阶段）

**首阶段准确范围**
- **做（仅限外壳）**：
  - 侧边栏：按 you.com 基线重构导航结构（顶级：工作台/知识库/偏好设置；分组：员工管理、行政管理、日常事务；用户菜单：个人资料/系统设置/退出登录），含分组展开/折叠、激活态高亮、折叠态响应式。
  - 顶部用户区：头像展示与编辑、个人资料/系统设置入口、通知中心入口。
  - 底部管理条（ManagementBar）、浮动 Dock（毛玻璃与主题化样式，事件契约不变）。
  - 全局搜索入口、ChatPanel 内嵌面板（外壳内嵌层）。
  - 统一视图映射模块（第 4 节）与单点切换开关接线（仅 dev/preview 启用，见第 3 节）。
- **不做**：任何业务模块组件（员工/社保/宿舍/知识库/档案/食堂/发票/办公劳保/反馈/部门等）及其页面内逻辑；内容区布局治理（P10 已完成，不在本阶段重复）；新功能开发。
- **保持**：系统头部标题字体与动效（第 2 节硬性约束）；既有权限显隐逻辑（菜单/按钮按角色显隐行为与迁移前一致）；全局事件契约。

**交付物**：新壳组件集（侧栏/用户区/管理条/Dock/通知/个人设置入口）+ 视图映射模块 + 单点切换接线 + 配套测试。

**依赖**：阶段 0。

**明确不改范围**：`renderMainContent` 各业务分支逻辑；业务模块组件；后端；系统头部标题（第 2 节）。

**完成条件**：验证计划第 6 节首阶段最小用例集通过——L1（外壳配套 Vitest 全绿）、L2（`rbac.spec.ts` 等回归通过）、L3（浅/深截图人工核对通过）；无已知严重 BUG。

### 阶段 2：旧业务接入与不可达组件归属

**交付物**
- 矩阵 3.2–3.7 中 ✅ 项全部接入新壳导航（复用现有组件，仅挂载，不改逻辑）。
- 三个不可达组件归属落地（审计日志、系统监控、组织管理，见第 6 节）。
- ⏳ 后续接入项（入职/转正/离职/人事异动）在新壳保留入口，并按矩阵 4.2 登记升级为 ✅ 的验收标准（组件 + API + 测试）。
- 🛑 占位项（共 9 项）统一接入占位视图并登记归零批次（见第 7 节）。

**依赖**：阶段 1。

**明确不改范围**：不实现占位项与后续项的真实业务功能（属于后续 P 阶段，仅登记批次）；不修改既有业务组件逻辑；后端不做迁移相关改动。

**完成条件**：G2（既有 3 个 E2E spec 全通过）+ G3（关键视图截图人工核对）+ G4（前端 lint/tsc/build、后端 go test/vet/build 全绿）；矩阵三态状态与基线一致；占位计数已登记。

### 阶段 3：最终切换与收尾

**交付物**
- 生产环境移除迁移开关（固定新壳为最终形态）的确认。
- 最终切换签署记录（按第 8 节门槛）。
- 验证记录表归档，结果同步至 `TODO.md` 与 agentmemory【任务规划】/【测试记录】。

**依赖**：阶段 1、2。

**明确不改范围**：不新增功能；不调整系统头部标题（第 2 节）；不做占位项业务实现。

**完成条件**：第 8 节最终切换门槛全部满足（含 ⏳ / 🛑 全部归零、无占位残留硬性条件），主协调者签署切换。

## 6. 三个已有但不可达组件的归属

现状：`AuditLogs`（`audit`）、`SystemMonitoring`（`monitoring`）、`OrganizationManagement`（`organization`）在 `page.tsx` 已有渲染分支，但侧边栏无入口，用户不可达。三组件状态为「组件已存在、入口待归属」；`app-sidebar.tsx` 存在基于 admin 邮箱的失效过滤分支（`user?.email === "admin@example.com"`），随入口归属一并清理（P12.1）。

| 组件 | 当前视图值 | 归属（基线入口） | 权限依据 | 接入步骤 |
| --- | --- | --- | --- | --- |
| 审计日志 `audit-logs.tsx` | `audit` | 系统设置内（建议：系统设置 → 审计日志） | `users.view` | ① 在 you.com 基线补充入口 → ② 新壳侧栏/系统设置内挂载 → ③ 权限过滤（替换失效 admin 邮箱过滤分支） |
| 系统监控 `system-monitoring.tsx` | `monitoring` | 系统设置内（建议：系统设置 → 系统监控） | `users.view` | 同上 |
| 组织管理 `organization-management.tsx` | `organization` | 行政管理组（建议：行政管理 → 组织管理） | `department.view` | 同上 |

规则（沿用矩阵第 6 节维护机制）：
1. **顺序不可颠倒**：先改 `/home/you.com/src/App.tsx` 基线（定义导航入口），再同步矩阵 3.6 状态，最后在 hr-office 新壳挂载组件。
2. 归属完成后必须通过 `app-sidebar.tsx` 权限过滤断言复核入口可达性（无权限用户按矩阵隐藏）。
3. 归属在阶段 2 内完成，作为该阶段交付物之一。

## 7. 占位策略

1. **统一占位组件**：新壳中所有无真实组件的基线导航项（劳动合同、奖惩记录、培训管理、合同管理、安全管理、能耗管理、车队管理、职业卫生、社保业务，共 9 项）渲染统一的 `PlaceholderView`（遵循 `docs/ui-design-p9.md` 空状态规范：图标 + 名称 + 说明 +「功能开发中，敬请期待」文案）。
2. **占位必登记**：每项占位必须登记归零条件（矩阵 5.2 五条：权限依据、后端 API、前端组件挂载、验收证据、入口可达性）与计划批次；批次登记在 `TODO.md`，本方案不复制其细节。
3. **归零节奏**：每批次结束时「临时占位」必须归零，或已在 `TODO.md` 明确下批次计划（该节奏仅适用于分阶段开发期间，允许保留已登记占位）；连续两批次未动的占位项视为优先级缺陷，上报主协调者（矩阵 5.3）。**该节奏不得作为最终切换保留占位的理由**——最终切换前 ⏳ 与 🛑 必须全部清零，全部旧功能真实接入（见第 8 节）。
4. **文案集中管理**：占位文案集中在一个占位组件文件内，便于按批次清理时整体替换；占位残留检测（可选自动化，`rg "功能开发中|敬请期待"`）命中即失败，白名单仅限分阶段开发期间使用，**最终切换前必须撤销白名单并全量清零**。

## 8. 最终切换门槛

「切换」指主协调者签署——以新壳为准、迁移视为完成且不再回退。必须**同时满足**（与 `docs/frontend-ui-migration-verification.md` 第 8 节一致）：

1. 阶段 0–3 全部完成；G0–G4 门槛通过，G5 回退演练完成且有记录。
2. **旧功能全量真实接入（硬性）**：矩阵中 ⏳ 与 🛑 状态全部转为 ✅，全部旧功能真实接入基线导航；无任何占位页面或「功能开发中，敬请期待」等占位文案残留（撤销白名单后残留检测零命中）。分阶段期间的"已登记占位 / 已登记下批次计划"不作为保留占位的理由。
3. AC-1 至 AC-9 全部验收主张有对应证据，无未解释偏差。
4. 无已知严重 BUG：E2E 无控制台异常、无 5xx 接口错误、无深色模式破相。
5. 视觉截图人工确认通过（浅/深各至少一张关键视图）；系统头部标题字体与动效经核对未变（第 2 节）。
6. 验证记录表归档完整，结果同步至 `TODO.md` 与 agentmemory【任务规划】/【测试记录】。

任一条件未满足时，切换挂起，由主协调者发起偏差处置（修复后重跑受影响门槛），禁止带失败项签署。

## 9. 风险与回退

### 9.1 风险清单

引用 `docs/frontend-ui-migration-verification.md` 第 2 节，迁移实施同步执行其缓解措施：

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| `.next` 目录竞争 | dev server 与 `next build` 并行互相覆盖产物，E2E/build 随机失败 | 验证计划第 5 节串行约束（硬性） |
| 陈旧 `.next` 缓存 | E2E 验证旧产物，误判结果 | 验证前清理 `frontend/.next` |
| jsdom 能力有限 | 布局、动画、滚动无法在单元层验证 | 布局类断言走 L2/L3，不依赖 L1 |
| 无截图基线 | 视觉回归只能人工比对 | 首阶段人工核对，不引入新依赖 |
| 外壳影响全站布局 | 外壳尺寸改动波及所有模块页面 | 回归既有 3 个 E2E spec + 登录冒烟 |
| 深色模式易漏测 | 深色破相难以发现 | L3 强制浅/深各截图一张 |
| 权限逻辑与外壳耦合 | 外壳重构连带改动权限显隐分支 | 以 `rbac.spec.ts` 作为外壳回归主入口 |
| 环境依赖 | E2E 需后端与种子账号，环境不一致误报 | seed-e2e 幂等创建 + 独立测试库 |

迁移特有的补充风险：

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 视图映射错配 | 新壳导航项指向错误视图或未登记视图 | 阶段 0 映射表定稿 + 阶段 1 映射模块测试 |
| 单点切换开关泄漏到生产 | 生产环境出现未验证外壳 | 第 3 节隔离原则：开关仅 dev/preview，生产固定最终形态 |
| 系统头部标题被新壳样式覆盖 | 违反第 2 节硬性约束 | 复刻时原样复用类与动画，验收时逐项核对 |

### 9.2 回退策略

1. **单点切换回退**：新壳切换通过唯一装配点开关控制，发现回归时在 dev/preview 关闭开关即可整体回到旧壳（不涉及生产）。
2. **代码级回退**：迁移前基准 commit 已记录（阶段 0）；按验证计划 G5 执行回退演练——git 临时分支 checkout 迁移前 commit 并 `npm run build` 通过，确认回退路径存在后回到当前分支并清理临时分支。G5 仅验证可回退性，不恢复代码。
3. **回退触发条件**：任一完成条件（G 门槛 / AC 主张 / 切换门槛）未满足且无法在合理批次内修复时，由主协调者决定回退，并记录原因与证据。
